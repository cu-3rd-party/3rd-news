# Архитектура

## Сервисы

| Сервис | Ответственность | Состояние |
| --- | --- | --- |
| `main` (API) | приём новостей, таксономия, разрешение меток, выдача, админ-API, аутентификация | Postgres |
| `main` (worker) | вызов классификаторов, скачивание вложений | Redis-очередь |
| `classifier-*` | превращает новость + таксономию в набор меток | без состояния |
| `parser-*` | читает канал и шлёт новости в `/add_news` | без состояния |
| `admin-ui` | ревью и настройка | без состояния |

Классификаторы и парсеры — не плагины. Это самостоятельные HTTP-программы,
которые главный сервис знает только по URL из админки. Поэтому их можно писать
в других репозиториях и на других языках; `packages/contracts` — удобство, а не
требование.

## Поток данных

```
парсер ──POST /api/v1/ingest/news──▶ main
                                     │ пишет news + attachments
                                     │ применяет дефолты источника и метки парсера
                                     │ создаёт по задаче на каждый классификатор
                                     ▼
                              Redis: jobs:classify, jobs:media
                                     │
                                     ▼
                                  worker
                          ┌──────────┴───────────┐
              POST /classify│                    │GET вложения по URL
                            ▼                    ▼
                    classifier-*            файлы на диск
                            │
              ответ 200 ────┤──── ответ 202 ──▶ позже POST /api/v1/classification/callback
                            ▼
                    news_labels (мнение)
                            │
                            ▼
              news_effective_labels (итог) ──▶ GET /api/v1/news
```

## Модель данных

Ключевое решение: **таксономия — это строки в БД, а не enum в коде.**

* `facets` — независимые оси классификации (важность, поток, тип, формат…).
  У оси есть `type`: `single` (одно значение) или `multi` (несколько), и флаг
  `required`.
* `facet_values` — значения оси. На каждом значении висят `synonyms` и
  `match_patterns` (их читает regex-классификатор) и `ai_hint` (его читает
  LLM-классификатор). То есть правила классификации редактируются в админке.
* `news` — сама новость: `body_md`, `source_link` / `source_text`,
  `published_at` (со стороны источника) и `received_at` (время прихода в сервис).
* `news.is_gold` — эталонная новость для измерения классификаторов.
  Размечена руками, но в примеры (`knowledge.collect_examples`) никогда не
  попадает, иначе тест утёк бы в подсказку. Выгрузка —
  `GET /api/v1/admin/news/export`, измеритель — `tools/eval`.
* `attachments` — картинки, PDF, видео. Либо пришли файлом, либо скачиваются
  воркером по URL.
* `news_labels` — **все** мнения: ручное, дефолт источника, метка парсера,
  ответ каждого классификатора. Ничего не перезаписывается.
* `news_effective_labels` — итог разрешения. Только по этой таблице фильтрует
  выдача, поэтому фильтрация — это простой `EXISTS`, а не пересчёт на лету.
* `classifiers` — реестр классификационных сервисов: URL, секрет, приоритет,
  порог уверенности, произвольный `config`, который прокидывается сервису.
* `api_keys` — ключи с правами (`ingest` / `read` / `editor` / `admin`) и
  необязательным `filter_preset`, который сужает выдачу на стороне сервера.

## Разрешение меток

Функция `app.labels.recompute_effective` пересчитывает итог для одной новости:

1. Мнения классификаторов отбрасываются, если классификатор выключен, у него
   снят `auto_apply` или уверенность ниже его порога.
2. Если ось указана в `news.manual_facets`, остаются только ручные метки.
   Пустой список тоже значим: «редактор посмотрел и решил, что ось не применима»
   — иначе это было бы не отличить от «ещё никто не размечал».
3. Остальные сортируются по `(вес источника мнения, приоритет классификатора,
   уверенность)`. Побеждает верхний ярус целиком; для оси `single` берётся один
   лучший.

Веса: `manual 400 > source_default 300 > parser 200 > classifier 100`.

Пересчёт запускается при: приёме новости, ответе классификатора, ручной правке,
удалении оси или значения, и по кнопке «пересчитать» в админке.

## Очередь

Redis-списки + `BLPOP`. Задачи публикуются **после** коммита транзакции, иначе
воркер может взять задачу, чья строка ещё не видна. Провалившаяся задача
возвращается в очередь до `NEWS_CLASSIFICATION_MAX_ATTEMPTS` раз.

Этого достаточно для потока в тысячи новостей в сутки. Если понадобится больше
гарантий — заменяется реализация `app/queue.py` (`enqueue` / `consume`), вызовы
менять не нужно.

## Статусы новости

```
pending ──классификация завершена──▶ published        (если auto_publish и все
   │                                                   обязательные оси заполнены)
   └──────────────────────────────▶ needs_review      (иначе)
                                          │
        редактор ─────────────────────────┴──▶ published | rejected | archived
```

Наружу по умолчанию отдаётся только `published` (`NEWS_PUBLIC_STATUSES`).
Клиент с правом `editor` может запросить любые.

## Что осознанно упрощено

* **Поиск** — `ILIKE` по заголовку и телу. Для настоящего полнотекстового поиска
  нужен `tsvector` + GIN-индекс; это отдельная миграция и один `where`.
* **Хранилище файлов** — локальный том. Замена на S3/MinIO — это `save_bytes` и
  `public_url` в `app/storage.py`.
* **Дедупликация** — по `(источник, external_id)` и по хэшу текста внутри одного
  источника за 30 дней. Кросс-источниковые перепечатки сейчас не склеиваются.
