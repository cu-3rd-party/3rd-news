# Архитектура v2

## Границы

Главный сервис — пакет с четырьмя режимами запуска: API, outbox publisher,
pipeline worker, index worker.
Парсеры и классификаторы независимы; общий Python-код находится только в
`packages/python`. Связь определяется версионированными контрактами, а не
импортами чужих реализаций.

Factory/lifespan и ресурсы следуют предоставленному примеру backend:
`create_app` создаёт приложение, lifespan открывает и закрывает необходимые
ресурсы, readiness проверяет их текущее состояние, middleware задаёт request ID
и единый безопасный формат ошибки. Конкретные адаптеры создаются в `lib/infra/resources.py`.

Каждый сервис расположен в `services/<name>`: код в `lib/`, тесты в `test/`,
рядом `main.py`, `Dockerfile`, `pyproject.toml` и `uv.lock`. Фабрика приложения —
`lib/app.py`, настройки и инициализация — `lib/core/`, HTTP — `lib/handlers/`,
сценарии — `lib/interactor/`, сущности — `lib/domain/`, DTO — `lib/dto/`,
адаптеры и ресурсы — `lib/infra/`.

Зависимости направлены внутрь: handlers → interactor → domain;
infra реализует порты interactor. ORM-модели отделены от доменных
сущностей и HTTP DTO. Домен не импортирует SQLAlchemy, HTTP или брокер.
Константы и runtime-настройки централизованы в настройках соответствующего
сервиса; изменяемая таксономия и редакционные правила хранятся в БД.

## Источник истины и версии

PostgreSQL хранит неизменяемые submissions, канонические news и их версии,
связи с исходными публикациями, независимые мнения классификаторов/парсеров/
редакторов, итоговую разметку, processing jobs, upload intents, пользователей,
ключи, сессии, outbox/inbox и аудит.

Ручное решение имеет приоритет над source defaults, затем parser, затем
classifier. Пустая ручная ось — решение редактора, а не отсутствие решения.
Set, explicit-empty и release записываются как неизменяемые ревизии ручного
решения. Merge/split переносят их provenance, включая решения без строк меток.
История повторных попыток не затирается. Примеры для AI выключены по умолчанию;
при включении выборка ограничена опубликованными non-gold ручными примерами и
исключает новости от источников с `skip_classification=true`.

Таксономия имеет глобальную монотонную ревизию. Любое изменение facet или value
увеличивает её, поэтому classifiers видят новую версию даже при изменении
описания, hint, synonym или pattern без изменения slug.

Идемпотентность приёма основана на stable client key или source/external_id.
Payload fingerprint обнаруживает повторное использование ключа для другого
содержимого. Хеш похожего текста создаёт предложение редактору, не удаляет
самостоятельную публикацию. Merge/split сохраняют provenance и требуют ревью.

## Доставка и восстановление

1. API сохраняет submission и outbox в одной транзакции, затем отвечает 202.
2. Outbox worker арендует записи, публикует события и ждёт подтверждения NATS.
3. Pipeline получает идентификаторы, проверяет inbox и актуальность задания,
   выдерживает cooldown через расписание БД, получает текст и вызывает внешние
   классификаторы вне DB-транзакции.
4. Результат проходит schema/business validation, нормализацию и разрешение
   мнений. Сохранение проверяет версию попытки, создаёт новую версию и outbox.
5. Index worker получает published/updated/deleted, читает актуальную БД,
   изменяет Meilisearch и ждёт завершения его асинхронной задачи.

Изменения политики классификатора, таксономии и редакционных правил создают
durable rematerialization job в той же транзакции. Worker пересчитывает новости
ограниченными чанками с курсором, восстанавливается по lease после сбоя и для
каждой записи создаёт событие поисковой проекции. Пока job pending/running либо
проекция отстаёт, пользовательские detail/feed/RSS/media закрываются барьером.

Сообщение NATS содержит идентификаторы и метаданные, не тексты, файлы или секреты.
Повторная доставка допускается. Сбой после публикации до отметки delivered
вызывает повтор, а не потерю; повторный результат не создаёт вторую версию.
Просроченные leases/callbacks восстанавливаются; попытки ограничены, финальная
ошибка видна редактору. Исчерпанные доставки сохраняются в отдельном durable DLQ;
подтверждение исходного сообщения следует только после подтверждения записи DLQ.
Admin API показывает ошибки outbox и позволяет запланировать аудитируемый replay. Допускается повтор внешнего AI-вызова после аварии,
но не повторное применение результата.

## Поиск и доступ

Meilisearch — перестраиваемая проекция. Feed выполняет поиск и фильтрацию
в индексе, detail/admin читают PostgreSQL. Индекс имеет checkpoint актуальности.
При ограничении видимости БД фиксирует барьер; до подтверждённой синхронизации
устаревшая выдача, counts и facets не возвращаются. Кандидаты перепроверяются
по текущим правам в БД. Это сознательная потеря доступности вместо утечки.

Единая политика read применяется к list/detail/RSS/media. Ключ с preset не
может расширить права query-параметрами. Недоступный объект по ID отвечает 404.
Медиа GET/HEAD/Range проходят авторизацию на каждом новом запросе; private
bucket и upload endpoint не дают альтернативного пути чтения.

## AI и файлы

AI — внешний классификатор; поставщик модели выбирается его конфигурацией.
Он возвращает версионированные факты, метки и evidence, а не исполняемый код.
Важность рассчитывается обычным кодом по версионированным данным правил:
urgency + impact + editorial_priority; каждый компонент 0–100, старт нейтральный.

Raw AI payloads шифруются, доступны ограниченной роли и удаляются через 30 дней.
В обычные логи не пишутся payloads, Authorization, cookie или presigned URLs.
Сохраняются проверенные результаты, версии схем/промптов/моделей и диагностические
метаданные. Резервное копирование должно отдельно учитывать срок хранения raw
payloads; стандартный Compose не настраивает внешние backup-системы.

Presign создаёт upload intent и временный key. Complete проверяет фактический
размер/хеш и закрепляет объект отдельно от перезаписываемого upload key.
URL-вложения загружаются потоково с сетевыми и ресурсными ограничениями.
Извлекается только пассивный текст; изображения и AV хранятся без OCR/ASR.

## Эксплуатация

Compose v2 использует новые volumes и сеть thirdnews-v2. Миграции — отдельный
одноразовый процесс. Stateless pipeline масштабируется количеством реплик;
PostgreSQL остаётся арбитром ownership/версий. CPU Ollama — проверочный профиль.
Без данных об оборудовании и нагрузке production SLO не заявляется.

Полный Event Sourcing, внутренние микросервисы, подписки и уведомления не
добавляются: для этой версии достаточно версий, append-only мнений и outbox.
