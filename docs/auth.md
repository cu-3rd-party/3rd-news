# Авторизация

Требование к сервису — уметь несколько схем сразу и добавлять новые, не трогая
ручки. Поэтому аутентификация устроена как **цепочка бэкендов**: каждый смотрит
на запрос и либо выдаёт `Principal`, либо отходит в сторону.

```
NEWS_AUTH_BACKENDS=["api_key","jwt","session"]
```

Порядок — это порядок проверки. Неизвестное имя падает при старте, а не молча
отключает схему.

## Что уже есть

| Бэкенд | Для кого | Как передаётся |
| --- | --- | --- |
| `api_key` | парсеры, боты, серверные клиенты | `X-API-Key: tnk_…` |
| `jwt` | скрипты, мобильные клиенты, внешний издатель токенов | `Authorization: Bearer …` |
| `session` | админка и браузерные клиенты | кука `news_session` |
| `sso` | заглушка под кампусный SSO | — |

`Principal` — общий результат для всех схем:

```python
@dataclass
class Principal:
    kind: str            # какой бэкенд авторизовал
    subject: str         # стабильный идентификатор для логов и аудита
    display_name: str
    scopes: set[str]     # read | ingest | editor | admin
    user_id: str | None
    role: str | None
    filter_preset: dict  # серверные фильтры, которые нельзя расширить запросом
```

Ручки требуют не «бэкенд», а право: `require_read`, `require_ingest`,
`require_editor`, `require_admin`. Поэтому новая схема авторизации автоматически
работает везде.

## Права

| Право | Что даёт |
| --- | --- |
| `read` | читать выдачу `/api/v1/news` |
| `ingest` | слать новости в `/api/v1/ingest/news` |
| `editor` | админ-ручки по новостям и разметке, чтение любых статусов |
| `admin` | всё, включая ключи, пользователей, классификаторы, таксономию |

Роли пользователей отображаются в права так: `admin → {read, ingest, admin}`,
`editor → {read, editor}`, `reader → {read}`.

## JWT

Свои токены сервис выдаёт сам (`POST /api/v1/auth/token`, HS256 на
`NEWS_SECRET_KEY`). Чтобы принимать токены **внешнего** издателя, достаточно
конфига — код менять не нужно:

```bash
NEWS_JWT_ALGORITHM=RS256
NEWS_JWT_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----…"
NEWS_JWT_ISSUER=https://sso.example.edu/
NEWS_JWT_AUDIENCE=3rd-news
```

Права берутся из claim `scope` (строка через пробел) или `scopes` (список);
опционально читаются `role`, `user_id`, `filter_preset`.

## Как добавить SSO

Форма кампусного SSO пока неизвестна, поэтому в
[`services/main/app/auth/sso.py`](../services/main/app/auth/sso.py) лежит
заглушка с местом под реализацию. Три реалистичных варианта:

**1. Доверенный заголовок от прокси.** Перед сервисом стоит oauth2-proxy или
Keycloak gatekeeper, он аутентифицирует и передаёт `X-Forwarded-User`. Бэкенд
читает заголовок и находит `User` по `sso_subject`. Просто, но безопасно
только если прокси — единственный путь к сервису (иначе заголовок подделает кто
угодно).

**2. OIDC id_token.** Клиент присылает JWT провайдера, мы проверяем его по JWKS.
По сути это `JwtBackend` с другим источником ключа и кэшем JWKS.

**3. CAS / SAML.** Редирект-флоу; после успеха выдаём обычную сессионную куку.
Это не бэкенд, а пара ручек `/auth/sso/login` и `/auth/sso/callback` —
`SessionCookieBackend` дальше работает как есть.

Во всех случаях в модели `User` уже есть `sso_subject` и `sso_provider`, а
пароль необязателен: аккаунт может существовать без него.

Порядок действий: реализовать `authenticate` в `SsoBackend`, добавить `"sso"` в
`NEWS_AUTH_BACKENDS` (лучше первым), ручки не трогать.

## Ключи

Выпускаются в админке, показываются один раз, хранятся как SHA-256 (значения
случайные и высокоэнтропийные, KDF тут не нужен — а вот пароли пользователей
хэшируются argon2).

У ключа могут быть:

* набор прав;
* привязка к источнику — тогда парсер может не указывать `source_key`;
* `filter_preset` — серверное сужение выдачи, которое запросом не обойти
  (см. [`docs/contracts/delivery.md`](contracts/delivery.md#ограничения-на-стороне-ключа));
* срок действия.

Отзыв действует немедленно.
