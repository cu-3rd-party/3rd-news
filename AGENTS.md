# Соглашения репозитория

## Архитектурный принцип

Парсеры и классификаторы — внешние программы, а не части главного сервиса.
Любая правка, которая заставляет главный сервис знать что-то про конкретный
парсер или классификатор, скорее всего неверна. Общая поверхность — только
`packages/contracts` и то, что описано в `docs/contracts/`.

## Правила

* **Таксономия — это данные.** Никаких enum'ов с осями классификации в коде:
  админ добавляет ось через API/админку, без миграции и деплоя.
* **Меняете контракт — меняете `docs/contracts/`** в том же коммите. Ломающее
  изменение требует новой версии в `CONTRACT_VERSION`.
* **Меняете модели — добавляете миграцию.** `alembic revision --autogenerate`,
  затем прочитать результат: автогенерация не видит переименования.
* **После изменений обновляйте связанную документацию** — README, docs/, и
  комментарии в коде.
* Задачи публикуются в очередь **после** коммита транзакции.
* Ответы классификаторов никогда не затирают чужие мнения: пишем строку в
  `news_labels` и пересчитываем `news_effective_labels`.

## Инструменты

* Python 3.11+, зависимости пиньятся в `requirements.txt` каждого сервиса.
* Фронтенд: bun (`bun install`, `bun run dev`, `bun run build`), не npm/node.
* Тесты: `python -m pytest` из корня. БД для них не нужна.
* Каждый сервис собирается с контекстом сборки в корне репозитория — иначе
  `packages/contracts` не попадёт в образ.

## Пакет `app`

Все три Python-сервиса называют свой пакет `app` (это правильно для контейнера
с одним сервисом). Из-за этого в тестах на `sys.path` кладётся только
`services/main`, а классификаторы грузятся по пути — см. `tests/conftest.py`.
