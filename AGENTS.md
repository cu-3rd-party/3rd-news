# Соглашения репозитория

## Архитектурный принцип

Парсеры и классификаторы — внешние программы, а не части главного сервиса.
Любая правка, которая заставляет главный сервис знать что-то про конкретный
парсер или классификатор, скорее всего неверна. Общая поверхность — только
`packages/python/contracts` и то, что описано в `docs/contracts/`.

## Правила

* **Таксономия — это данные.** Никаких enum'ов с осями классификации в коде:
  админ добавляет ось через API/админку, без миграции и деплоя.
* **Меняете контракт — меняете `docs/contracts/`** в том же наборе изменений. Ломающее
  изменение требует новой версии в `CONTRACT_VERSION`.
* **Меняете модели — добавляете миграцию.** `alembic revision --autogenerate`,
  затем прочитать результат: автогенерация не видит переименования.
* **После изменений обновляйте связанную документацию** — README и docs/.
* Задачи публикуются в очередь **после** коммита транзакции.
* Ответы классификаторов никогда не затирают чужие мнения: пишем строку в
  `news_labels` и пересчитываем `news_effective_labels`.

## Инструменты

* Python 3.14, только uv. У каждого сервиса собственные `pyproject.toml`, `uv.lock` и `.venv`.
* HTTP — aiohttp; httpx/httpx2 не использовать. Общий Python-код — только в `packages/python`.
* Фронтенд: bun (`bun install`, `bun run dev`, `bun run build`), не npm/node.
* Проверки: `make test`, `make lint`, `make integration` (те же цели через just).
  Unit-тесты не требуют БД; integration/E2E используют отдельный стенд.
* Каждый сервис собирается с контекстом сборки в корне репозитория — иначе
  `packages/python/contracts` не попадёт в образ.

## Создание сервисов

Следуйте архитектуре предоставленного примера backend: application factory,
lifespan, ресурсы с явными create/close/status, request ID, единая обработка
ошибок и health endpoints. Доменные сущности отделены от ORM и DTO.
Каждый сервис: `services/<name>/lib`, `test`, `main.py`, `Dockerfile`,
`pyproject.toml`, `uv.lock`. В `lib`: `core`, `domain/entities`, `dto`,
`interactor/{errors,interfaces/{clients,storage},use_cases}`,
`infra/{clients,storage}` и `handlers`. `lib/app.py` — application factory,
а `handlers/top.py` регистрирует отдельные APIRouter. Реализации клиентов и
хранилищ явно наследуют соответствующие interfaces. Ошибки находятся только
в `interactor/errors`, один публичный класс размещается в одном файле.
`src`, `bootstrap`, `presentation`, `ports` и параллельные legacy-модули не создавать.
Общих runtime-файлов вне packages/python не создавать.

Настройки сервисов читаются только через pydantic-settings. Подключения задаются
атомарными полями scheme/host/port/user/password/name; готовые URL вычисляются
в Settings. Режим процесса задаётся переменной окружения, собственные CLI-аргументы
не используются. В maintained source не оставляются комментарии и docstrings.

## Изменения

Коммиты строго запрещены. Старый заменённый код и неиспользуемые настройки
удаляются; параллельный legacy API не сохраняется. Существующие данные,
секреты и volumes автоматически не удаляются.
